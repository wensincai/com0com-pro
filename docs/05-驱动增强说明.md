- 日期：2026-11-23

- 状态：**已编译通过（0 error）；未在真机加载验证（本机 HVCI 开启，需 VM）**

## 1. 问题：为什么原版 com0com 删不掉被打开的端口

`sys/pnp.c` 的端口 FDO 对 PnP 查询移除的处理是硬性拒绝：

```c
case IRP_MN_QUERY_REMOVE_DEVICE:
  if (pDevExt->openCount)
    status = STATUS_DEVICE_BUSY;   // ← 有句柄打开就拒绝
  else
    pIrp->IoStatus.Status = STATUS_SUCCESS;
  break;
```

`openCount` 在 `sys/openclos.c` 中维护：每个 `CreateFile("\\.\CNCAn")` 加一，
每个 close 减一。于是 `setupc remove` 在端口被应用占用时必然失败——这正是
VSPD 的差异项之一（VSPD 允许删除已打开端口）。

**为什么不能简单删掉这个检查**：通过 `IRP_MN_REMOVE_DEVICE` 直接
`RemoveFdoPort()` 会立即 `IoDeleteDevice()` 释放设备扩展。已打开句柄随后到达的
cleanup/close IRP 会落到已释放内存上 → 蓝屏。所以必须“延迟释放”。

## 2. 改动内容

| 文件 | 改动 |
|---|---|
| `sys/com0com.h` | 端口扩展新增 `forceRemove`、`removing`、`pRemoveWorkItem`；声明 `FinishDeferredRemove` / `RemoveWorkItemRoutine` |
| `sys/adddev.c` | 端口创建时从注册表 `ForceRemoveOpenPorts`（DWORD，默认 0）读取开关；新增延迟移除收尾函数（PASSIVE_LEVEL 释放资源、`IoDeleteDevice`、释放延迟期间持有的对象引用） |
| `sys/pnp.c` | `QUERY_REMOVE`：`forceRemove=1` 时不再返回 `STATUS_DEVICE_BUSY`；`REMOVE_DEVICE`：有打开句柄时进入延迟移除（标记 `removing`、`HidePort` 隐藏端口、`ObReferenceObject` 保活、预分配 work item、正常把 IRP 传下去） |
| `sys/openclos.c` | 最后一个句柄 close（`openCount` 减到 0）且处于延迟移除时，`InterlockedCompareExchange` 抢占一次性状态后 `IoQueueWorkItem` 收尾 |
| `sys/read.c` / `sys/write.c` | 延迟移除中的端口对新 I/O 返回 `STATUS_DELETE_PENDING` |

### 状态机

```
正常 ──(REMOVE, openCount>0, forceRemove=1)──► removing=1
                                                │ HidePort：新 CreateFile 失败
                                                │ 新 Read/Write → DELETE_PENDING
                                                ▼
                                  最后一个 close ──► removing=2, 入队 work item
                                                ▼
                     FinishDeferredRemove：释放池/字符串 → IoDeleteDevice → 解引用
```

## 3. 如何开启（按端口）

开关存放在端口设备的**设备参数键**（`PLUGPLAY_REGKEY_DEVICE`，即
`HKLM\SYSTEM\CurrentControlSet\Enum\<实例ID>\Device Parameters`），
与 `PortName`/`EmuBR` 等参数同一位置：

```bat
:: 1) 找到端口实例 ID（管理员）
pnputil /enum-devices /class Ports /instanceid | findstr /i "COM0COM"

:: 2) 写入开关（对 CNCA0 / CNCB0 各做一次）
reg add "HKLM\SYSTEM\CurrentControlSet\Enum\<实例ID>\Device Parameters" ^
  /v ForceRemoveOpenPorts /t REG_DWORD /d 1 /f

:: 3) 让端口重新创建（卸载并重装该对，或重启）
x64\setupc.exe remove 0
x64\setupc.exe install 0 -

:: 4) 验证：开着端口也能删
::    （在应用中打开 COM 或 CNCA0，然后）
x64\setupc.exe remove 0
```

> 关闭：把值改为 0（或删除该值）后重建端口。
> 默认 0 = 完全保持原版行为。

## 4. 风险与验证计划（必须）

**风险等级：高。** 延迟移除涉及设备对象生命周期，任何引用计数错误都可能导致
蓝屏（`BAD_POOL_CALLER` / `USE_AFTER_FREE` 类）。因此：

1. 该特性**默认关闭**，仅显式写注册表才启用；
2. 本机（VBS/HVCI 运行中）**无法加载测试签名驱动**，未做运行验证；
3. 必须在关闭 Secure Boot + HVCI 的虚拟机中验证，检查项：
   - [ ] 打开端口 → `setupc remove` 成功，设备管理器条目消失
   - [ ] 移除后应用侧 Read/Write 返回 `ERROR_DEVICE_REMOVED` / `DELETE_PENDING`，不崩溃
   - [ ] 应用关闭句柄后 `!poolused` / Driver Verifier 无泄漏、无 use-after-free
   - [ ] Driver Verifier（Special Pool + Pool Tracking + Force IRQL Checking）跑 30 分钟无 bugcheck
   - [ ] 未开开关时行为与 3.0 原版一致（回归）
4. 验证通过前，发布包应保持开关默认关闭。
