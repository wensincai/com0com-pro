# com0com-pro：技术选型

- 日期：2026-11-23

## 1. 选型总原则

1. **内核驱动不动**：com0com.sys 已验证可编译（0 warning）且功能覆盖超预期，重写风险/收益比极差
2. **新代码集中在用户态**：bundle 引擎、CLI、GUI、服务、API 都是用户态程序，选型自由度大
3. **沿用已验证的团队技术栈**：putty-rs（Rust + egui）经验可直接迁移

## 2. 内核层：C / WDM（保持 com0com.sys）

| 候选 | 评估 | 结论 |
|---|---|---|
| C / WDM（现状） | 13,226 行，0 warning 编译，签名流程已打通 | ✅ 保持 |
| C / KMDF 重构 | 需重写全部 13k 行，引入回归风险 | ❌ |
| Rust 驱动（windows-drivers-rs / drvtpl） | 生态早期、WDM 串口类参考缺失、HVCI 下调试成本高 | ❌（5 年内不评估） |

驱动侧唯一预计改动：FR-C2（强删打开端口，pnp.c）、FR-C3（会话命名空间，adddev.c），均为小步 C 修改。

## 3. 用户态控制面：语言对比

| 候选 | 优势 | 劣势 | 结论 |
|---|---|---|---|
| **Rust** | 无数据竞争（bundle 引擎是并发密集：多端点泵+事件路由）；windows crate 一等 Win32 FFI；tokio 异步泵；egui GUI 有现成经验（pt-gui）；测试友好 | 团队需 Rust 技能（已具备）；GPL 生态绑定简单 | ✅ **选定** |
| C++20 | 与 setup.dll 同栈；Win32 原生 | 并发安全靠纪律；GUI 需另选框架；与 setupg 同类问题重演 | ❌ |
| C# / .NET 8 | GUI 快（WPF）；P/Invoke 可用 | 引擎热路径 GC 抖动；服务+CLI+库三形态打包冗长 | ❌ |
| Go | 并发好 | Win32 FFI 二等公民；GUI 生态弱 | ❌ |

## 4. Rust 技术栈明细

| 层 | 选型 | 理由 |
|---|---|---|
| 异步运行时 | tokio（`rt-multi-thread`, `net`, `io-util`, `time`, `sync`, `macros`, `process`） | 端点泵是 IO 密集；`process` 调 setupc |
| Win32 / 串口 | `serialport` 4.x（跨平台枚举+读写，BlockingFd→spawn_blocking 泵）；ACL/会话查询用 `windows` crate | serialport 纯 Rust，免 cargo:rustc-link 兼容问题 |
| 序列化/配置 | serde + serde_json（配置 JSON、日志 JSONL） | — |
| 日志 | tracing + tracing-subscriber | — |
| CLI | clap derive | — |
| GUI | egui/eframe 0.33 | putty-rs 已验证 |
| 错误 | thiserror（库）/ anyhow（CLI） | — |
| 单测 | 内置 `#[test]` + 内存端点 | CI 可跑，不依赖真实串口 |

## 5. 进程形态

```
ccp-core（库）──┬── ccp-cli（ccp.exe，控制台）
                ├── ccp-service（Windows 服务：开机重建 bundle + 活动日志）
                └── ccp-gui（egui 管理界面）
```

- 引擎运行在 **服务进程**，CLI/GUI 经命名管道 JSON-RPC 与其通信（控制面/数据面分离，NFR-4）
- 开发期可 `ccp serve --foreground` 前台跑引擎，无需装服务
