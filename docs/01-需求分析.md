# com0com-pro：需求分析

- 日期：2026-11-23
- 定位：以开源 com0com（3.0.0.0，GPL）为内核基础，补齐商业 VSPD（Eltima Virtual Serial Port Driver 11）的功能，形成可长期演进的虚拟串口套件
- 项目目录：`E:\reverseEngineering\20261112\com0com-pro`
- 基础代码：`E:\reverseEngineering\20261112\com0com`（已完成 VS2022+WDK 现代化迁移，见其 MIGRATION-REPORT.md）

## 1. 背景与目标

com0com 是 2012 年冻结的 GPL 虚拟串口对驱动：能创建 CNCA0<->CNCB0 型空调制解调器端口对，波特率仿真、缓冲溢出仿真、噪声注入、引脚互联等能力，但**管理粒度只有"一对端口"**，缺少 VSPD 的端口捆绑（split/join/merge/share）、权限、日志、现代化 GUI 等能力。

VSPD（商业，$89.95–139.95）功能强但闭源。本项目目标：

1. **保留** com0com 驱动内核（已验证可编译、测试签名通过）
2. **新建用户态控制面**（bundle 引擎 + CLI + GUI + 服务），补齐 VSPD 功能差距
3. **分阶段**做少量驱动级增强（自定义引脚接线、按用户会话端口等）

## 2. com0com 与 VSPD 功能差距矩阵

| 能力 | com0com 3.0 | VSPD 11 | 差距归类 |
|---|---|---|---|
| 无限数量虚拟串口对 | ✅（上限 100 万对） | ✅ | 无 |
| 自定义端口名（含占用真实名 COM1） | ✅ PortName/RealPortName | ✅ | 无 |
| 完整硬件控制线仿真（DTR/DSR/RTS/CTS/DCD/RI） | ✅ | ✅ | 无 |
| HandFlow（硬件 + Xon/Xoff） | ✅ | ✅ | 无 |
| 严格波特率仿真 | ✅ EmuBR | ✅ | 无 |
| 缓冲溢出仿真 / 接收超时参数 | ✅ EmuOverrun、AddRTTO/AddRITO | 部分 | com0com 反超 |
| 线路噪声注入（EmuNoise） | ✅ | ❌ | com0com 反超 |
| LSR/MODEM_CONTROL 扩展 IOCTL | ✅ | 未知 | com0com 反超 |
| 标准/回环/自定义引脚接线方案（pinout） | ✅（cts/dsr/dcd/ri 每脚可自由接线到本地/对端 RTS/DTR/OUT1/OUT2/OPEN/常 ON±，见 sys/pinouts.c） | ✅ 预设方案 + GUI | 仅差 GUI 预设 |
| 一个端口拆分给多个端口（split） | ❌ 需第三方 hub4com | ✅ 内置 | **bundle 引擎** |
| 多端口合并为一个（join/merge） | ❌ | ✅ 内置 | **bundle 引擎** |
| 复杂端口捆绑（多入多出，混合虚实端口） | ❌ | ✅ | **bundle 引擎** |
| 真实端口间流量转发 / 重定向 | ❌（com2tcp 另装） | ✅ | **bundle 引擎** |
| 多应用共享一个真实 COM 口 | ❌ | ✅ | **bundle 引擎** |
| 端口被其他应用打开时强制删除 | ❌（PnP 移除会失败） | ✅ | **驱动级（难）** |
| 每端口读/写权限控制 | ❌ | ✅ | **bundle 引擎可先做** |
| 应用使用端口的"活动日志" | ❌ | ✅ | **bundle 引擎** |
| 重启后登录前自动重建端口 | ✅（PnP 设备持久化） | ✅ | 无 |
| 按用户会话（RDP）独立端口名 | ❌ | ✅（Global/session 两种） | **驱动级（难）** |
| DLL API 供自有程序直接控制 | ⚠️ setup.dll（简陋，无公开文档化 API） | ✅ OEM DLL | **新控制面 API** |
| 现代化 GUI（拖拽式端口管理） | ⚠️ setupg（.NET 2.0 风格表格） | ✅ | **新 GUI** |
| 安装后无需重启 | ✅ | ✅ | 无 |
| WDM/WMI/电源管理/PnP | ✅ | ✅ | 无 |
| 64 位 / VMware / 超线程 | ✅ | ✅ | 无 |

结论：**差距集中在两类**——
- A 类（用户态可解决，不碰内核）：split / join / merge / 复杂捆绑 / 转发 / 共享 / ACL / 活动日志 / API / GUI / pinout 预设
- B 类（需要改驱动）：强制删除已打开端口、按用户会话端口

## 3. 功能需求（FR）

> 状态（2026-11-23，P1–P5 完成后）：✅ 已实现 · 🚧 部分 · ❌ 未实现

### FR-A 用户态控制面（P0，本项目的核心增量）
- 🚧 **FR-A1 bundle 引擎**：端点抽象（串口/TCP/内存测试端点）+ 四种路由策略（copy-all / round-robin / first-writer-wins / one-to-one）已实现，覆盖 split / merge / share / redirect；`complex`（多入多出规则路由）仅有类型占位
- ✅ **FR-A2 端口对管理**：PairManager 封装 `setupc.exe`（list/install/install_many/remove/change/ensure_pair 幂等）
- ❌ **FR-A3 每端口 ACL**：配置模型已有 `AclRule`，引擎侧未强制（需引擎代开句柄，P6）
- ✅ **FR-A4 活动日志**：JSONL（open/close/read/write/drop/error/bundle-open/close），引擎写入
- ✅ **FR-A5 持久化与开机重建**：bundles.json + `ccp-service`（SCM 服务，`%ProgramData%\com0com-pro\bundles.json`）
- 🚧 **FR-A6 编程 API**：Rust 库 API 可用；命名管道 JSON-RPC 未做（P6）

### FR-B 管理界面（P1）
- ✅ **FR-B1 CLI（ccp.exe）**：`validate/init/list/pair/serve/ports/service` 子命令
- ✅ **FR-B2 GUI**：egui 管理界面（bundle 列表/编辑、引擎启停、活动日志实时视图、串口与端口对列表）

### FR-C 驱动级增强（P2，改 sys/ C 代码）
- ✅ **FR-C1 pinout 预设方案**：驱动已支持每脚接线，控制面可直接用 `cts=/dsr=/dcd=/ri=` 参数
- 🚧 **FR-C2 强制删除已打开端口**：驱动已实现（`ForceRemoveOpenPorts` 注册表开关 + 延迟移除 + work item 收尾），**默认关闭，待 VM 验证**（见 docs/05）
- ❌ **FR-C3 按会话端口**：未做（P6）

### FR-D 工程化（P0）
- FR-D1 全部文档（需求/代码分析/选型/架构）随代码演进
- FR-D2 构建脚本化（驱动 MSBuild + Rust cargo），签名脚本复用 com0com 的 tools/
- FR-D3 许可证合规：com0com.sys 为 GPL v2，**整个项目须以 GPL v2+ 分发**；新增用户态代码同样 GPL

## 4. 非功能需求（NFR）

| 编号 | 要求 |
|---|---|
| NFR-1 | bundle 引擎单链路吞吐 ≥ 5 MB/s（对齐 VSPD 宣称量级），CPU 占用低（事件驱动，无轮询） |
| NFR-2 | 用户态代码 `#![forbid(unsafe_code)]`（Win32 FFI 封装 crate 内除外，需评审记录） |
| NFR-3 | 驱动侧改动不破坏现有测试签名流程与 Inf2Cat 校验 |
| NFR-4 | 控制面崩溃不影响已有数据链路（引擎独立进程/服务化） |
| NFR-5 | 测试：核心路由逻辑 100% 单测（内存端点）；E2E 对真实/虚拟端口 |

## 5. Non-goals（本期）

| 项 | 理由 |
|---|---|
| 重写内核驱动（Rust 驱动 / KMDF 重构） | 13,226 行 WDM 代码久经使用且已可编译；重写风险远大于收益 |
| TCP/Telnet/RFC2217 重定向器 | 与 hub4com/com2tcp 重叠，后续再评估 |
| 蓝牙/蓝牙串口仿真 | 场景小众 |
| WHQL 认证流程 | 依赖 EV 证书与 Partner Center，规划期事项 |
